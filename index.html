part one — the diagnosis

Why Claude Code alone isn't enough.

Matt's skills exist because a fresh Claude Code agent — powerful as it is — fails in four predictable ways. Recognize them, and the journey ahead starts to make sense.

  1. i.

    Misalignment

    The agent confidently builds the wrong thing. You said "pomodoro timer" and it shipped a stopwatch; you said "auto-flip to break" and it added a confirm dialog. The fix isn't a better prompt — it's a grilling ritual that surfaces every assumption before a line of code is written.

    cure → /grill-me, /grill-with-docs

  2. ii.

    Verbosity

    Without shared vocabulary, every conversation re-explains what "completed" means, how "long break" differs from "break." Tokens burn, context fills, drift creeps in. The fix is a living CONTEXT.md — a project glossary the agent actually reads.

    cure → ubiquitous language, CONTEXT.md

  3. iii.

    Broken code

    An agent without a test loop is an agent flying blind. It will swear the timer works, then carry overrun across phase boundaries and silently shorten every break. The fix is a feedback loop tight enough that lying becomes impossible: tests first, then the code that turns them green.

    cure → /tdd, /diagnose

  4. iv.

    Architectural decay

    Matt's framing: "AI has simply accelerated software entropy. Codebases are falling apart faster than they ever have before." Every feature lands without the agent considering the whole codebase — small weirdnesses snowball into a ball of mud. The fix isn't willpower, it's ritual: routinely deepen the modules, name the abstractions, record the hard-to-reverse decisions.

    cure → /improve-codebase-architecture, ADRs (sparingly)

The eight skills that follow are the cure, sequenced. Read them as a journey, not a menu. ↓

I phase one

monday · 09:14 · opening the toolbox

Setup.

Before the first conversation about the pomodoro, install the skills and let one of them set up the others. The repo gains a .claude/ directory, a CONTEXT.md stub, and the labels your future issues will need.

You opened a fresh repo this morning — pomodoro/, empty except for a README.md with one line of vision: "a quiet timer that just works — 25 on, 5 off, no accounts, no cloud." Nothing else. No tests, no PRD, no issue tracker spun up.

Resist the urge to start prompting. The first skill you install is the one that installs the others. It scaffolds the conventions every later skill assumes: a place for ADRs, a triage label set on your issue tracker, a CONTEXT.md that begins life empty but will fill itself as you talk.

why this matters Skills compose through shared artifacts — CONTEXT.md, docs/adr/, the label taxonomy. Without setup, every skill works in isolation. With it, they form a system.

/git-guardrails-claude-code Run this once per machine before you commit anything. It installs Claude Code hooks that block git push --force, git reset --hard, branch deletes, and other one-keystroke catastrophes. Not project-specific — but the moment to install it is right now, while you have zero work to lose.

/setup-pre-commit Would normally fire here too — Husky + lint-staged for format/typecheck/tests on commit. We're skipping it for this build because the pomodoro app is pure vanilla JS with no npm. Honesty over checklist completeness: a skill that doesn't fit your stack is just noise.

II phase two

monday · 09:42 · the grilling

Align.

One sentence of vision is not a spec. /grill-with-docs turns Claude into the rubber duck that argues back, forcing every assumption to the surface while building a shared glossary as you go. The output isn't code — it's a shared mental model and a populated CONTEXT.md.

The grilling is uncomfortable on purpose. Every "I think we want…" gets met with "what specifically? what's the failure mode if not?" The skill walks down each branch of what Matt — following Frederick P. Brooks — calls the design tree: pick a node, name its trade-offs, resolve them, descend. Don't write code until every branch is named.

For the pomodoro, the grill exposes the first hidden decision in under five minutes: when a work session hits zero, does the timer auto-flip to break, or wait for the user to confirm? You hadn't decided. You'd been about to ship the wrong UX.

By the time you exit, CONTEXT.md has gained a glossary with session, completed, auto-flip, long break, tick — each with a one-line definition. Every future skill, every future session, will read this file and stop asking what these words mean.

matt's rule "When you have a codebase, use /grill-with-docs. When you don't have a codebase, use /grill-me." Matt has moved /grill-me to his productivity folder — for non-engineering use cases (he cites a viewer who used it to gather stories for a eulogy). For software work, even on day one of a fresh repo, /grill-with-docs is the engineering version because the act of writing the glossary is the work.

why the docs matter "You really can nail down and get a magical alignment between you and the AI where you just have to use far fewer words to communicate what you mean." Once CONTEXT.md exists, the agent stops re-asking what "auto-flip" means, file names become consistent with domain terms, and replies tighten because both sides are speaking the same vocabulary.

how much harder does it actually grill? One reviewer ran the same project description through four planning approaches: Claude Code default plan mode — 4 questions. Codex plan mode — 3. Superpowers plug-in — 8. /grill-me — 13. The resulting spec grew from a 55-line prompt to a 146-line document — with concrete data models, named technical approaches (e.g. "vector search vs. OpenAI query for AI search"), and per-feature fields the original draft glossed over. The grilling isn't just longer; it's structurally different.

/ubiquitous-language The standalone predecessor that /grill-with-docs absorbed. Reach for it directly if you want to only sharpen the glossary without a full grilling session — e.g., when refining CONTEXT.md after a feature has shifted the domain language.

artifact — CONTEXT.md (after the grill)

## Domain

- session — a single work or break phase, fixed length.
- completed — a counter, incremented when a work session ends
  (not when a break ends).
- auto-flip — at the boundary, the timer transitions automatically
  to the next phase with no user input. Overrun is discarded.
- long break — every 4th completed work session is followed by a
  15-minute break instead of a 5-minute one.
- tick — one step of forward time. The UI owns the cadence;
  the module is pure logic.
III phase three

monday · 10:30 · from talk to tickets

Spec.

Two skills, back to back. /to-prd compresses the grill into a single product document and files it as the parent issue. /to-issues slices that PRD into vertical tickets — each one shippable end to end — ready for an agent to grab.

This is the joint where most teams — human or agentic — lose the thread. A PRD that lives in a Notion doc nobody opens, issues sliced horizontally by layer ("backend ticket / frontend ticket / db ticket") that no single agent can finish alone.

Matt's skills go the other way. /to-prd writes the spec into the issue tracker — the same place the work will happen. /to-issues then breaks it into vertical slices: "timer counts down with pause and resume" is one slice, soup to nuts. The first slice ships in 30 minutes. The fourth ships the product.

vertical slices, defined A slice is shippable if a user could (in principle) get value from it alone. "Add a phase enum" is not a slice. "Timer counts down with pause and resume" is. Matt calls these tracer bullets — each one cuts through every integration layer so the unknowns surface in the first slice, not the last.

ready for agent Each sliced issue gets a brief and a ready for agent label so an autonomous loop — Matt's Ralph loops — can pull it off the queue, implement, commit, close, and grab the next. The skill's purpose is to make tickets agent-ready, not just human-readable.

what the polished videos don't show In his unscripted live stream Matt admits two things the curated tutorials elide. First, "I generally don't read these research documents. The important thing for me is the conclusions we came to." The PRD is for the agent's context, not your review. He does read CONTEXT.md — the glossary, not the spec. Second, on viewer questions about reviewing the plan: "people over-review their plans and I think this is a classic mistake… what they need to be doing is getting to code." The skills exist to finish the planning, not to extend it.

/prototype Optional but useful here. Before TDD-ing the real timer, sketch a 30-line throwaway in a scratch file: just enough markup and JS to see if a single MM:SS countdown feels right. Throw it away. The skill exists specifically to escape the TDD discipline when you're validating a UX hunch, not building production code.

/triage Not just a bug-intake filter — /triage manages the entire backlog. It runs a label state machine: needs triage → needs info → ready for agent → ready for human → won't fix. Matt frames it as "Q management... a translation layer between the humans creating these tickets and the AI that's going to implement them." It pairs naturally with /diagnose: if a triaged item is a bug, the same session can drop into a reproduction loop on the spot.

IV phase four

monday · 11:15 · red, green, refactor

Build.

/tdd picks up a sliced issue and runs the red-green-refactor loop strictly: write a failing test, make it pass with the smallest possible change, refactor with tests as a net. Claude is bad at flying blind — the test loop is the cure.

If you've watched Claude implement a feature without tests, you know the failure mode: code that compiles, looks plausible, and silently does the wrong thing. /tdd inverts the order. The test comes first. The implementation exists only to satisfy it.

For issue #2, the first test is two lines of intent: a fresh pomodoro reports phase=work, remainingMs=25*60_000, completed=0, isRunning=false. It fails — createPomodoro doesn't exist yet. Claude writes the smallest factory that returns the right shape. Test passes. Then: start, advance time, expect remaining to decrease. Fail. Implement tick(). Pass. Pause / resume — the trickiest test in slice 1, because the implementation must not consume time spent paused. Claude almost ships it wrong; the test catches it.

Four slices, twelve assertions, one running app — embedded below.

discipline check The skill will refuse to write implementation before a test exists. Slice 3 (auto-flip) tries to ship without a test for the "overrun is discarded" rule; the skill pushes back, the test gets written, and we catch a real bug a week before it would have surfaced in production. Review what the agent wrote, though — Owain Lewis (AI TDD video) flags that agents will sometimes generate redundant tests or tests that exercise library code rather than yours. "Worth reviewing the tests as well as reviewing the implementation."

when refactor is fine to skip The "refactor" step of red–green–refactor isn't mandatory every iteration. After a 29-line green implementation in the AI TDD demo, Lewis notes: "we don't really need to do anything here in terms of simplification." If the green code is already shaped right, move to the next test. The discipline isn't the ritual — it's the *option* of refactoring under test cover.

the rule — one test at a time "LLMs love to create huge horizontal layers. They'll add 90 different tests in one edit and try to one-shot an implementation that passes all of them. You end up with a lot of crap tests." The non-negotiable rule: one test, watch it fail, minimal implementation, green, next test. Each test guides the implementation; bulk-test-then-bulk-impl produces tests that don't guide anything.

why read tests, not implementations "I don't necessarily read all of the implementations. I've seen it go red and then go green, I feel pretty confident." The watchable red→green transition is the trust signal. Review the test titles to understand what's covered, then QA the running behavior; the implementation between them is structurally pinned.

/caveman — mind the dumb zone Matt notes that despite advertised 1M-token context windows, "for proper smart tasks you've only got about 120k to work with." Past that, attention diffuses and quality degrades. Switch to /caveman mode mid-build — ~75% fewer tokens per response — to extend the session before you hit the dumb zone and need /handoff.

the QA loop — not a skill, a pattern Once /tdd finishes the slices, Matt runs an explicit QA pass. Open a fresh Claude session: "Take the last N commits and create a step-by-step QA plan as a GitHub issue." Walk the plan in the running app, file new issues for anything you find, restart the Ralph loop to fix them while you keep QA-ing. Repeat until satisfied. Tests don't replace the human eye on the UI — they buy you the right to trust the implementation between QA passes.

/dispatching-parallel-agents Slices #4 (persistence) and #5 (notifications) genuinely share no state — one writes localStorage, the other calls Notification. Dispatch them to two parallel agents and merge at the end. The skill includes the coordination ritual (separate branches, dependency-free tests) that makes parallelization actually faster than sequential.

Ralph loops — the night shift, mechanically Matt's autonomous runner is a real Docker-based tool he provisionally calls Sand Castle: mounts your working dir into a container, lets Claude commit inside, then pulls the commits out as patches and applies them to your local repo. Kicked off via pnpm ralph with a 100-iteration cap; runs through the GitHub backlog one issue at a time, closing each as it lands. Typical night shift in his videos: ~30 min to ~1.5 hr wall-clock. The day/night-shift framing comes from his friend Jamon: humans grill & plan during the day, the agent implements at night while you walk to the kitchen.

// slice 1 / test 3 — the test that pinned the pause/resume invariant
test("pause freezes; later resume continues from there", () => {
  const clock = makeClock();
  const p = createPomodoro({
    workMs: 60_000, now: clock.now, storage: makeStorage(),
  });
  p.start();
  clock.advance(10_000); p.tick();
  p.pause();
  eq(p.getState().isRunning, false);
  clock.advance(30_000); p.tick();
  eq(p.getState().remainingMs, 50_000,
     "30s of pause does not consume time");
  p.start();
  clock.advance(20_000); p.tick();
  eq(p.getState().remainingMs, 30_000,
     "after resume + 20s, remaining is 30s");
});

V phase five

monday · 15:48 · care, not heroics

Maintain.

All four slices green. But the build surfaced two issues worth handling before declaring v0.1 done: a subtle bug in phase transitions (overrun carryover), and a quietly-shallow design choice (the module had been about to grow its own setInterval). Two skills, two artifacts.

The bug. The slice 2 test — "work→0 auto-flips to break with full breakMs" — failed on the first implementation: a 1500ms tick into a 1000ms work session left the break at 1500ms remaining, not 2000ms. The agent had carried the 500ms overrun forward. /diagnose doesn't guess; it runs the loop — reproduce, minimize, hypothesize, fix. The fix lands with a regression test and an ADR that names the choice: overrun is discarded; each new phase starts fresh.

The shallow module. Mid-build, the implementation was about to grow an internal setInterval — cleaner-looking but harder to test (every test would need a fake timer). /improve-codebase-architecture read the module with one question: what does this own, and what should it own? Answer: it owns state transitions. It does not own time. The UI does. The skill writes the ADR; the module gets a tick() method instead; tests use a manual fake clock; everyone wins.

the rhythm of maintenance Bug → /diagnose → fix + regression test. Drift → /improve-codebase-architecture → refactor + ADR. Same loop, different trigger. Neither skill is heroic; both make care routine.

tactical vs strategic "Agents are really really good tactical programmers. They're able to get on the ground and make changes quickly, but they need someone on the level above them who is the strategic programmer." /improve-codebase-architecture only works with auto-mode off — the AI is the sergeant scouting the codebase for "deepening opportunities" (shallow modules with wide interfaces), but you, the general, make the calls. The skill then ships a refactor RFC to /to-issues for an AFK agent to execute. Run it every few days.

accelerated software entropy "AI has simply accelerated software entropy. Codebases are falling apart faster than they ever have before, because every time you make a change that doesn't take into account the entire codebase you introduce little weird things... until you end up with a huge ball of mud." Maintenance isn't a side quest; with AI on the keyboard it's the only thing keeping the codebase navigable.

/zoom-out Run this before /improve-codebase-architecture, not in place of it. /zoom-out answers "what does this codebase actually look like from above?" — and that altitude is the precondition for spotting which modules are shallow. We used it to notice that app.js was about to grow a timer responsibility that didn't belong there.

ADRs — only for the hard-to-reverse An ADR isn't for "we picked Vitest over Jest" — that's swappable. ADRs are for decisions that calcify the codebase: ours (0001 overrun discarded, 0002 module owns no clock) both shape every future feature touching the timer. If undoing the choice in six months would be cheap, skip the ADR.

artifact — docs/adr/0002-module-owns-no-clock.md

# 0002 — createPomodoro owns no clock

status: accepted   date: 2026-05-28

context. The pomodoro module was about to grow an internal
setInterval to drive its own ticking. This is the obvious shape —
"the timer ticks itself" — but it makes the module shallow:
its interface would balloon with start/pause/reset and also
implicit clock-coupling that every test would need to stub.

decision. The module owns state transitions only.
Time is advanced by an external caller via tick(). In production
the UI calls setInterval(() => pomodoro.tick(), 250). In tests,
the harness calls tick() directly after advancing a fake clock.

consequences. + Module is trivially testable with no
fake-timer scaffolding. + The boundary between "pure logic"
and "real I/O" is explicit and narrow. − Callers must
remember to wire a tick driver — but the failure mode is loud
(the timer doesn't move) and immediate.
VI phase six

monday · 18:02 · passing the baton

Handoff.

Context windows fill. Sessions diverge. A side-quest opens mid-grill. /handoff compresses just the relevant slice of the current session into a markdown file the next reader — human or agent — can resume from cleanly. Not a summary. A continuation. Most often fired mid-session, not at end of day.

Pomodoro v0.1 is shipped — four slices green, two ADRs filed, twelve tests passing in tests.html. The session that built it is 16k tokens deep, well inside the smart zone. But you noticed a refactor opportunity in app.js halfway through Phase V that's "totally out of bounds out of scope from my current session." Extending the chat would dilute it; /compact would clobber the current progress. /handoff is the third option: peel off just that slice, ship it to a fresh agent, keep this session pure.

The file goes to the OS temp directory, not your repo. Matt is explicit: "these handoff files are disposable… not something to be kept around for a long time to rot in your codebase as documentation." It contains only what the next session can't reconstruct from the code itself — open questions, deferred decisions, the "why" behind anything non-obvious — and uses pointers to GitHub issues, ADRs, and CONTEXT.md rather than duplicating their content.

matt's rules for a good HANDOFF.md (1) Save to $TMPDIR, never the repo. (2) Use pointers, never duplicate. (3) Redact API keys, passwords, PII — markdown ends up in places you don't expect. (4) Always describe why you're handing off — without a stated purpose, the agent can't write a useful document. (5) Include a Suggested Skills section so the receiving agent knows whether to invoke /grill-with-docs, /diagnose, /prototype, etc.

handoff ↔ prototype: the DIY sub-agent loop The richest pattern Matt describes: in the middle of a grilling session you hit a question the agent can't answer without seeing code. /handoff to a fresh agent that runs /prototype. That agent learns. /handoff the learnings back to the original grilling session. The original session resumes with the new knowledge in 200 tokens instead of 16k. "It's almost like you've done a kind of DIY sub-agent."

/write-a-skill One more thing before we close: during the build we ran the same micro-routine twice — save state to localStorage, then notify subscribers. That's a pattern worth codifying. /write-a-skill scaffolds a new skill (frontmatter, progressive disclosure, examples) so your own recurring rituals become reusable. The meta-skill: building your toolbox as you build the thing.

appendix — skills we did not use

And why.

The journey covered every skill that genuinely fit this build — 17 of the 19 in the repo, each at the moment it would actually fire. Two skills didn't apply, and pretending they did would have been performative. Here's the honest accounting.

  • /migrate-to-shoehorn

    Replaces as assertions in tests with @total-typescript/shoehorn. We're vanilla JS — no TypeScript, no as casts — so the skill has nothing to migrate. Save it for the next TS project.

  • /scaffold-exercises

    Builds problem/solution/explainer directories for teaching material. This is a single-app build, not a course module. The skill is genuinely useful, just not here.

Every other skill from mattpocock/skills appeared above — in a terminal, in a callout, or in an artifact. Scroll back if you missed one.
