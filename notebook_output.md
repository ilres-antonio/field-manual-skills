### grill-me-rationale

> In Matt's own words, what specific failure mode does /grill-me prevent, and what does a good grilling session feel like compared to a bad one? Include any concrete examples Matt gives.

**The Specific Failure Mode Prevented**
According to Matt, **the primary failure mode `/grill-me` prevents is the AI rushing to generate a plan or document prematurely** [1]. Left to its own devices in standard plan mode, the AI tends to "spit out a plan really early" before a true "shared understanding" has been reached between the developer and the agent [1]. The `/grill-me` skill forces the AI to slow down, interview the user relentlessly, and walk down every branch of the "design tree" to resolve all technical dependencies before any code is written [1, 2]. 

**A Bad Grilling Session vs. A Good Grilling Session**
*   **A bad grilling session** feels tedious, repetitive, and overly wordy. Matt notes that without a shared vocabulary, the AI becomes "really really verbose" [3]. In a bad session, he found himself constantly having to interrupt the agent to remind it about existing terms, or they would spend time agreeing on "shared language" only for it to be forgotten because it wasn't documented anywhere [3].
*   **A good grilling session** feels like an engaging conversation with a highly competent lead developer who asks incredibly smart questions [4]. When the AI and the developer share the exact same vocabulary, **the session achieves a "magical alignment" where the AI seems to anticipate your thoughts before the words even come out of your brain** [5, 6]. A good session is characterized by "concise replies," allowing you to use "far fewer words to communicate what you mean" [6, 7]. 

**Concrete Examples**
Matt provides several concrete examples to illustrate what these sessions look like in practice:
*   **The Course Video Editor (Good Session):** Matt gave the AI some basic research about adding a split-pane document editing feature and invoked the skill [8, 9]. Instead of instantly writing a plan, the AI asked 16 deep, consecutive questions—ranging from where the document lives to the UI layout and the editing tool's shape [8]. This resulted in a thorough 45-minute planning discussion that locked in the exact requirements [10].
*   **Ghost Courses and Lessons (Good Session):** While planning a complex feature allowing him to create "ghost courses" (courses without a file path on his computer), the AI acted like his old lead developer, asking brilliant edge-case questions [4, 11, 12]. For instance, it successfully challenged him by asking a tricky question: if a "real course" has all of its real lessons deleted, does it revert back to being a "ghost course"? [13, 14].
*   **Pitches and Standalone Videos (Bad Session turning Good):** Matt experienced a frustratingly verbose session when trying to build a feature for video "pitches" and "standalone videos" [15, 16]. Because the AI didn't know what his domain-specific jargon meant, it wasted time asking for definitions or using overly long descriptions [3, 16]. This failure inspired Matt to upgrade his workflow with a new skill (`/grill-with-docs`) that feeds the AI a glossary upfront [17, 18]. Armed with this shared language, the AI immediately gave a great grilling session by asking highly precise questions, such as clarifying whether "one pitch holds many standalone videos or one pitch corresponds to exactly one standalone video" [19, 20].

### grill-with-docs-distinction

> How does /grill-with-docs differ from /grill-me in practice? When does Matt recommend each one? Quote him directly if possible.

**How `/grill-with-docs` and `/grill-me` Differ in Practice**

Matt Pocock originally designed the `/grill-me` skill to force the AI to "interview [the user] relentlessly... until we reach a shared understanding," making it walk down every branch of a design tree before writing code [1, 2]. However, in practice, Matt found that `/grill-me` often resulted in "really really verbose" sessions [3]. Because the AI lacked knowledge of specific domain jargon or project terms (like knowing what a "standalone video" means in a specific app), developers had to continually re-explain non-obvious concepts before any productive work could happen [3, 4].

To solve this, Matt created `/grill-with-docs`, which combines the original grilling mechanism with a "ubiquitous language" skill inspired by Domain-Driven Design [5, 6]. 

In practice, the key differences are:
*   **Documentation Integration:** `/grill-with-docs` actively looks for a `context.md` file at the root of your repository, which acts as a glossary of shared terms between you and the AI [6, 7].

### daily-skills

> Which 5 skills does Matt say he uses every single day? For each one, what is the trigger (the moment he reaches for it) and the artifact it produces?

**grill-me**
*   **Trigger:** Matt uses this skill when he has an idea and wants to reach a shared understanding with the LLM before committing to any code [1]. It prevents the AI from rushing into an overly eager plan [1]. 
*   **Artifact:** A relentless interview containing a deep series of questions [2, 3]. This conversation walks down the branches of a "design tree" to resolve dependencies and flesh out a thoroughly understood concept [1, 2, 4]. 

**write a PRD**
*   **Trigger:** He invokes this immediately after using `grill-me`, once a shared understanding of the idea's ramifications has been reached and he has decided to implement it [5].
*   **Artifact:** A Product Requirements Document (PRD) that clearly describes the "destination" of the project, including a problem statement, user stories, and implementation decisions [6, 7]. This document is submitted directly as a GitHub issue [8].

**PRD to issues**
*   **Trigger:** Used when he has the completed PRD (the destination) and needs to figure out the actual "journey" or plan to build it [4, 7].
*   **Artifact:** A Kanban board of different, independently grabbable GitHub issues [4, 7]. The PRD is broken down into "thin vertical slices" of work with defined blocking relationships, so autonomous agents can easily pick them up one by one [9, 10].

**TDD (Test-Driven Development)**
*   **Trigger:** Reached for during the execution phase when he wants to prompt his autonomous agents (which he calls "Ralph loops") to produce rock-solid implementations and increase code quality [4, 11, 12].
*   **Artifact:** Robust testing and implementation code [13]. The skill forces the agent into a "red green refactor" loop where it writes one failing test, implements the minimal code required to pass that specific test, and then refactors [11, 13].

**improve codebase architecture**
*   **Trigger:** Used periodically (e.g., once a week or after a surge of development) to clean up code, specifically when a codebase is poorly structured with unclear boundaries, which makes TDD difficult to execute [12, 14].
*   **Artifact:** It initially produces a numbered list of "deepening opportunities" (suggestions to turn shallow modules into deeper ones) and designs multiple potential interfaces to choose from [15]. Once a design is chosen, it outputs a refactor RFC (Request for Comments) as a GitHub issue [16].

### tdd-discipline

> What is Matt's specific TDD workflow with Claude Code? How does he keep the agent from skipping the red step? Any concrete examples of catching a bug because the test came first?

**Matt's TDD workflow** relies on a custom "TDD skill" that heavily restricts the AI to follow the traditional **red, green, refactor** methodology [1, 2]. By enforcing this process, he adds necessary back pressure against the AI's natural eagerness to speed through an implementation [3]. 

His specific workflow loops through the following steps:
*   **Red:** The agent must write an automated test first and confirm that it fails (making the Continuous Integration pipeline go "red") [2, 4]. 
*   **Green:** The agent then writes the **minimal implementation necessary** to make that specific test pass [4].
*   **Refactor:** Once the CI is "green," the agent can safely clean up, improve, and shape the code, knowing the tests will catch any newly introduced regressions [4].

**To keep the agent from skipping the "red" step or writing useless tests, Matt enforces a strict "one test at a time" rule** [5, 6]. Left to their own devices, LLMs have a tendency to create "huge horizontal layers" by writing 90 tests all at once and then attempting to "one-shot" the entire implementation to pass them [6]. By explicitly prompting the agent to perform an **incremental loop**—writing a single test, watching it fail, passing it, and only then moving to the next behavior—the agent stays focused and produces much higher quality tests that properly guide the implementation [5, 6]. Because Matt can visually see the agent's tests go from red to green, he feels confident trusting the AI's implementation before he goes in to do manual QA [5, 7]. 

**As for a concrete example of catching a bug** through this test-first approach, the sources provide a demonstration by Owain Lewis, who uses a nearly identical AI TDD skill [8]. While using Claude Code to build a session-based authentication service, the test-first workflow caught two specific bugs early in the process:
1.  **A library compatibility issue:** Immediately upon writing and running the initial failing tests for session token generation and password hashing, the agent caught and fixed an import/library compatibility error before writing the bulk of the logic [9].
2.  **A database mismatch bug:** Later in the process, the agent mistakenly set up the integration tests to run against an SQLite database, while the actual application relied on PostgreSQL [10]. When instructed to correct the test database to PostgreSQL, the previously "green" tests failed, revealing a **"real bug"** in the code that only appeared when running against the production-equivalent database [11, 12]. 

As demonstrated, enforcing the red/green loop provides the AI with a critical automated feedback mechanism, allowing it to instantly self-correct broken logic that would otherwise go unnoticed [13, 14].

### skill-sequencing

> What does Matt say about the ORDER in which skills should be applied? Are there hard dependencies (X must come before Y), or is order flexible?

Matt outlines a heavily utilized, logical pipeline for his skills, but **the order is entirely flexible and there are no strict hard dependencies** [1, 2]. 

**The Core Workflow (The "Happy Path")**
When building a new feature from scratch, Matt typically follows a specific sequence that takes an idea from initial planning all the way to execution:
1. **`grill-me` (or `grill-with-docs`)**: Used first to relentlessly question your idea until you and the AI reach a shared understanding [3, 4].
2. **`write-a-prd`**: Invoked immediately after grilling to formalize the conversation into a Product Requirements Document (PRD) [3, 5].
3. **`prd-to-issues`**: Used to break that PRD's destination down into an actionable journey of individual vertical slices (GitHub issues) [6-8].
4. **`tdd` (Test-Driven Development)**: Given to an autonomous "Ralph loop" agent to actually execute and implement the code for those issues using a red-green-refactor loop [2, 8, 9].

**Flexibility and Lack of Hard Dependencies**
While this pipeline is powerful, Matt emphasizes that the skills are modular tools that adapt to your context, meaning you can skip steps, interweave them, or jump in at different starting points:

* **Skills can dynamically skip redundant steps:** The `write-a-prd` skill actually contains instructions to interview you relentlessly before writing the document. However, if you already used `grill-me` earlier in the chat, the AI will recognize this, skip the interview phase, and jump straight to step four to draft the document [1].
* **Skills can be nested within one another:** You can pause a `grill-me` session partway through, use the `handoff` skill to spin up a separate agent to build a UI prototype, and then hand the prototype's learnings *back* into the original grilling session to finish your planning [10-12]. 
* **Different skills can act as entry points:** You don't have to start with ideation. If you run the `improve-codebase-architecture` skill, it generates a refactoring RFC as a GitHub issue, which you can then pass directly into the `prd-to-issues` skill [13, 14]. 
* **You can branch off immediately to fix things:** While using the `triage` skill to sort through a backlog of GitHub issues, you can fluidly invoke the `diagnose` skill in the exact same session to have the AI immediately reproduce and fix a bug on the spot [15, 16].

### anti-patterns

> What anti-patterns or common mistakes does Matt warn against in these videos? Anything specific to how people misuse Claude Code skills?

**Pushing the context window into the "dumb zone."** While models advertise massive context windows, their attention becomes diffuse as more tokens are added, leading to a "dumb zone" where responses degrade in quality [1]. Matt warns against extending a single session for multiple unrelated tasks (like noticing a separate bug and trying to fix it in the same chat), as this creates a "diluted context" [2]. Instead, he advises using the `/handoff` skill to extract the relevant context into a markdown file and pass it to a fresh, smart session [2], [3].

**Trusting default AI plan modes too much.** A major mistake developers make is trusting Claude Code's default plan mode, which tends to spit out a project plan "far too eagerly and early" [4], [5]. People accept these initial plans without thinking through all the necessary branches of a feature [6]. To combat this, Matt designed the `grill-me` (and later `grill-with-docs`) skill, which forces the AI to relentlessly interview the user and resolve all dependencies and ambiguities before writing any code [7], [8], [9].

**Allowing "horizontal" implementation and bulk testing.** LLMs naturally love to write "huge horizontal layers" by generating dozens of tests at once and then attempting to one-shot the entire implementation to pass all of them [10]. Matt notes this results in poor-quality tests. Instead, you should force the AI to write vertical slices using a strict Red-Green-Refactor loop—writing exactly one failing test at a time, implementing the minimal code to pass it, and then moving to the next [11], [12], [10]. Additionally, blindly trusting the tests an AI writes is a mistake; agents routinely make errors or test the wrong things, so humans must review the generated tests [13], [14]. 

**Letting AI code in a "garbage codebase."** AI has accelerated "software entropy," causing codebases to fall apart faster than ever if changes aren't made with the whole architecture in mind [15]. If your codebase is a "ball of mud" filled with shallow, tightly coupled modules, the AI will struggle to navigate it and will simply produce more garbage [16], [17], [18]. The AI needs clean, "deep modules" with clear testable interfaces to produce quality work [19], [18].

**Omitting the "why" and failing to establish a shared vocabulary.** If you only tell the LLM *what* you want to build without explaining the *why*, the AI cannot suggest smarter architectural alternatives or edge cases [20]. Furthermore, if you rely on undocumented domain jargon, you will waste tokens constantly re-explaining concepts, which makes the AI confused and verbose [21], [22]. Matt advises using "ubiquitous language" (like a `context.md` file) so both you and the AI share the exact same definitions for domain entities [23], [24].

**Letting handoff documents rot in your codebase.** When generating markdown documents to pass context between AI agents, a common mistake is saving them permanently in your repository. Matt insists these files are disposable and should be saved to your operating system's temporary directory so they don't "rot in your codebase as documentation" [25]. He also warns against duplicating information in these docs; they should simply use pointers to existing GitHub issues or codebase files [25].

**Misusing Architectural Decision Records (ADRs).** Creating ADRs for trivial choices—like swapping out two easily interchangeable libraries—is an anti-pattern. ADRs should strictly be reserved for non-obvious decisions where "the decision is hard to reverse" and carries significant long-term consequences for the codebase [26].

### surprising-claims

> Identify 3-5 claims Matt makes in these videos that would surprise a developer who has only read the GitHub README. Quote him directly.

**1. Huge context windows are largely an illusion for complex coding tasks due to the "dumb zone."**
While AI models advertise massive context windows (like Claude's 1 million tokens), Matt claims that reasoning breaks down long before you hit that limit. A developer expecting to dump an entire repo into the prompt might be surprised to learn: 
> "...even though Anthropic advertises a ton of context window on these models really for you know proper smart tasks you've only got about 120k to work with which means you need to budget really efficiently and you need to be aware of your context window at all times" [1].

**2. AI is actually making codebases fall apart faster, not just speeding up development.**
Instead of viewing AI as a magic tool that effortlessly builds software, Matt points out that relying on AI without strict architectural boundaries leads to rapid deterioration of code quality. 
> "...what's happening is that AI has simply accelerated software entropy in other words code bases are falling apart faster than they ever have before because every time that you make a change that doesn't take into account the entire codebase you are likely to introduce little things weird things that make the codebase harder to change..." [2].

**3. You don't actually need to read the code the AI writes if your testing loop is strict.**
Traditional developers are used to manually reviewing every line of syntax. However, Matt claims that if you force the AI to use a strict Red-Green-Refactor test-driven development (TDD) loop, you should review the tests and outputs rather than the implementations. 
> "I don't necessarily read all of the implementations because I've seen it go red and then go green I feel pretty confident that it's a reasonable testing the thing that it's supposed to And of course once this loop is over and it's committed to the branch I then go and QA that chunk of work" [3]. 

**4. Using native AI tools (like Claude's built-in "Ask Question" tool) is a waste of tokens.**
A developer might assume that using the AI's official tool-calling capabilities is the optimal way to build a workflow. However, Matt intentionally avoids them in his skills to save context space.
> "...if you have a choice between calling a tool and not calling a tool then like not calling a tool is always going to be more token efficient because every time you call a tool you need to wrap it in JSON" [4].

**5. AI prompts and "skills" do not need to be massive to be highly effective.**
There is a common misconception that getting good results from AI requires massive, hyper-detailed mega-prompts. Matt notes that his highly successful `grill-me` skill is only three sentences long. 
> "...skills don't have to be long to be impactful you've just got to choose the right words for the LLM at the right time..." [5].

### handoff-deepdive

> In the '/handoff is my new favourite skill' video specifically, what does Matt say is the failure mode that triggered him to build /handoff? How does it differ from naive 'summarize the conversation' approaches? What concretely goes into a HANDOFF.md that does NOT go into CONTEXT.md? Quote him directly where possible.

**The Failure Mode**
Matt explains that the trigger for building `/handoff` was encountering secondary tasks—like "a little refactoring opportunity"—that were "totally out of bounds out of scope from my current session" [1]. If he simply extended his current chat, he would create a "diluted context where I was half working on one thing half working on the other and I would definitely hit the dumb zone" [1]. 

**How it Differs from Naive "Summarize" Approaches**
Matt contrasts `/handoff` with the standard summarization approach (which he refers to as "compact"). "Compact" takes a long conversation and summarizes it so you can avoid the context limit "dumb zone," but it forces you to stay in "only really one session" [1, 2]. If Matt used compact to pursue a tangent, he "would clobber all of the progress that I'd made in my current session" [1]. 

Instead, `/handoff` allows parallel workflows. It is designed to "take just the slice that pertains to this extra bug fix hand it off to another session and then these two could just run independently," which allows Matt to "keep my current session pure" [3]. 

**HANDOFF.md vs CONTEXT.md**
While Matt doesn't discuss `CONTEXT.md` in the `/handoff` video, he breaks it down in a later video about his "ubiquitous language" skill. Based on his different workflows, here is concretely what goes into a `HANDOFF.md` that does *not* go into `CONTEXT.md`:

*   **Task Focus and Next Steps:** `HANDOFF.md` captures exactly what the new agent needs to do. Matt says if the user passes arguments, the skill will "treat those as a description as to what the next session will focus on and tailor the dock accordingly" [4].
*   **A "Suggested Skills" Section:** It explicitly tells the new agent which tools to use so that it can quickly adopt the right flavor for the session, meaning "it will invoke the skills needed like grill with docs or diagnose or prototype" [5].
*   **Disposable Artifacts (No duplication):** To save space, `HANDOFF.md` uses "pointers instead of... repeating everything that's in the document" [6]. Crucially, the file itself is highly ephemeral. Matt insists you should save these files to the operating system's temporary directory because they are "disposable" and "not something to be kept around for a long time to rot in your codebase as documentation" [6]. 

In contrast, `CONTEXT.md` is a permanent file meant to live at the root of your repository. It acts as "the thinnest layer of documentation" to permanently "document all of the shared language" and domain-specific terminology (a glossary) used by the project so the AI stops asking redundant questions [7-9].

Matt uses the **"improve codebase architecture skill"** to repair codebases that have deteriorated over time [1].

**Signs of an AI-Degraded Codebase**
Matt describes this degradation as a state of "accelerated software entropy" where codebases fall apart faster than ever [1]. Because AI often makes rapid changes without taking the entire architecture into account, it introduces **"little things weird things that make the codebase harder to change"** [1]. Over time, this snowballs into what he calls a **"huge ball of mud sloppy sloppy mud that is incredibly hard to reverse"** [1]. On a structural level, he notes that an AI-ruined codebase is typically characterized by having **"a ton of shallow modules in it or one that has very poor leverage for those modules or poor locality where lots of stuff is spread in lots of different places"** [2]. 

**The De-Slopping Process Step-by-Step**
The process of fixing this codebase relies heavily on keeping a human in the loop to make architectural decisions:
1. **Run the skill without auto-mode:** Matt initiates the "improve codebase architecture" skill but explicitly turns off auto-mode, noting that autonomous agents can do "funny things with these human in the loop style flows" [3].
2. **Explore for deepening opportunities:** The AI is instructed to explore the architecture to look for structural weaknesses and identify areas where shallow modules can be consolidated into deeper, more robust modules [2].

4. **Enter a grilling session:** The AI grounds the problem in concrete code and starts a back-and-forth "grilling session" with the user [4]. The AI proposes a new "module shape" and "TypeScript interface," and asks the user for feedback on specific design decisions [5, 6].
5. **Generate an issue for an AFK agent:** Once the human and AI agree on the new architectural shape, Matt uses his "PRD to issues" skill to turn the plan into a GitHub issue [6]. This allows an autonomous "AFK" (away from keyboard) agent to actually execute the refactor in the background [6].

**How This Differs From Normal Refactoring**
Unlike traditional refactoring where a human developer manually hunts down technical debt and writes the code to fix it, this method strictly divides the labor between human strategy and AI tactics based on a shared glossary of architectural terms (like "deep modules," "interfaces," and "seams") [7-10].

However, they require someone above them to act as the **"strategic programmer"** [11]. In this workflow, the AI surfaces the messy code and drafts the new design, but the human "general" makes the final judgment calls on what is actually good for the **"long-term health of the codebase"** [11].

### daily-skills-cadence

> In the '5 Claude Code skills I use every single day' video specifically, what is the typical ORDER Matt chains the skills in a single working day? In the "5 Claude Code skills I use every single day" video, Matt Pocock does not map out a specific daily schedule with times (such as a morning, midday, and afternoon routine) [1, 2]. Instead, he describes a **logical, step-by-step workflow** that he uses to take a feature from an idea to a fully implemented reality. 

**The Typical Order of Skills**
Matt chains his first four skills in a strict, sequential order:
1. **`grill me`**: He begins by invoking this skill to "flesh out an idea" and reach a shared understanding of the problem with the LLM before committing to code [1, 3]. 
2. **`write a PRD`**: Next, he says, "once I have reached a shared understanding with the LLM... if I then decide I want to implement it then I invoke my next skill which is a write a PRD skill" to turn the idea into a Product Requirements Document [3].
3. **`PRD to issues`**: Because the PRD only describes the "destination," he uses this next skill to break the document down into a Kanban board of independent, actionable tasks (the "journey") [4]. 
4. **`TDD` (Test-Driven Development)**: Finally, to execute the plan and write the actual code, he uses his TDD skill [1, 5].

Matt directly summarizes this specific sequence: 
> "so far the grill me skill can help you flesh out an idea the write a PRD skill can help you take that idea and turn it into a document and then the PRD... to issue skill helps you then turn that destination document into an actual journey but then how do you actually execute on that skill... we have got a TDD skill" [1, 5].

**Interleaving Sessions and Time Gaps**
While he doesn't specify exact time gaps, he does describe interleaving the work by handing the execution phase off to autonomous background agents. Once his `PRD to issues` skill generates GitHub issues, he steps back: "I have a Ralph loop that just loops over each issue until it's done" [6, 7]. 

He also notes that breaking a PRD down into independent issues is "really useful if you have a parallel agent setup where you can actually fire two agents at it at once for instance in like background tasks," indicating that multiple coding sessions happen concurrently in the background rather than him sitting and typing out the code sequentially [8]. 

**The Exception: `improve codebase architecture`**
His fifth skill, which is used for deep refactoring, is not part of this daily sequence. He specifically notes that he runs this skill less frequently, stating he uses it "every so often in a codebase you know once a week just to identify opportunities" [2]. Once the architecture skill identifies an opportunity and creates a GitHub issue, he feeds it back into the middle of his standard chain, using the `PRD to issues` skill to plot out the journey for the refactor [2, 9].

### rgr-fake-green-patterns

> In the 'Red Green Refactor is OP With Claude Code' video specifically, what are the concrete patterns LLMs use to 'fake green' tests (i.e., make tests pass without actually implementing the intended behavior)? Based on the provided sources, the specific video "Red Green Refactor is OP With Claude Code" **does not detail concrete patterns or provide specific examples of how LLMs fake passing tests.** 

However, the video does explain how the strict red-green-refactor discipline generally prevents an LLM from faking a green test:

*   **Observing the Failure:** The core of the discipline requires the agent to write an automated test first and confirm that it fails (the "red" phase) [1, 2]. Matt Pocock notes that it is "really comforting" to watch this sequence because he can verify in the continuous integration (CI) or agent output that the test initially failed [3].
*   **Isolating the Implementation:** Once the test fails, the agent writes the minimal code needed to pass the test (the "green" phase) [2]. Pocock observes that during this phase, the agent **"doesn't change anything about the test"** and **"doesn't try to like fake it to make it pass or anything."** [3]. He concludes that if the test was observed failing and then goes green without the test itself being altered, **"it's pretty hard for it to fake that"** [3].
*   **Preventing "Oneshot" Implementations:** While the video doesn't give examples of faking *specific* tests, it does point out a behavioral pattern where LLMs try to "create huge horizontal layers" and **"oneshot an implementation that passes all 90 of those tests"** at once in a massive file edit [4]. Pocock notes that this approach often results in "a lot of crap tests" [4]. 
*   **The Incremental Loop:** To catch and prevent this, Pocock's test-driven development (TDD) skill forces the agent to follow a strict rule: **only do one test at a time** [5]. By writing a single test, seeing it fail, and writing the minimal implementation before moving on to the next test, the tests are much more focused and effective at guiding the actual code quality [4]. 

Ultimately, Pocock states that as long as you QA the completed chunk of work yourself to catch anything the tests missed, you can easily flush out any bad tests that the agent may have generated [5].

### tdd-when-not-to

> In the 'How I Test With Claude Code (AI TDD)' video specifically, does Matt or the demonstrator (Owain Lewis) describe situations where TDD is overkill or counterproductive with AI agents? Any specific examples of when to skip the red step or use a lighter approach? Quote where possible.

In the "How I Test With Claude Code (AI TDD)" video, the demonstrator (Owain Lewis) does not describe any situations where TDD is overkill, nor does he suggest skipping the "red" (test creation) step. 

In fact, he strongly advocates for the exact opposite approach. Because AI agents remove the manual burden of writing tests, he concludes that "there's no reason not to write tests because it's so quick and easy to add tests to your codebase" [1]. He acknowledges that doing test-first development is "a little bit more effort to follow," but insists that the resulting consistency and code quality make it "well worth it" [2]. 

However, while he doesn't believe TDD itself is overkill, he does warn that **the AI agent can sometimes go overboard or test the wrong things**. He points out the following caveats when using AI for TDD:

*   **Agents can write redundant or unnecessary tests:** Lewis warns that AI might generate tests that "don't make sense" or end up "testing library functionality" rather than your actual code [3, 4].

### teach-deepdive

> In the 'Learn anything with the /teach skill' video specifically, what is the /teach skill designed to do, and what is the workflow Matt describes? What artifacts does it produce (e.g., a mission, glossary, learning record, resources list)? How does /teach differ from simply asking Claude to explain a topic? Quote him directly where possible.

The **/teach** skill is designed to act as a personalized AI tutor, taking everything Matt knows about teaching and putting "it inside a skill so that anyone could learn anything" [1]. The goal is to simulate a "real teacher who was teaching how I like to be taught and was totally aligned with my mission" [1]. A core philosophy behind the skill's design is teaching within the student's **zone of proximal development**, which ensures the user is "perfectly challenged but not intimidated" by keeping lessons "concise compact and exactly framed" [2]. Ultimately, it is designed to "give you the skills you need to feel confident to go out and work with a community and send you out into the world," rather than keeping you completely hooked on the AI [3].

**The Workflow:**
1. **Initialization:** The user starts by running the `teach` command in an empty directory inside their coding agent [4]. 
2. **Context Gathering:** On the first pass, the agent figures out the user's "mission" (why they want to learn) and searches the web for "primary source" resources [5].
3. **Interactive Learning:** The agent generates the first lesson. The user walks through this lesson, which includes interactive elements and quizzes to develop a "feedback loop" [5, 6].
4. **Progress Tracking:** Once a user completes a lesson or returns for a new session, they can "fill in the teacher on what I've been doing since I last had a session" [7]. The agent updates its records and dynamically generates the next tailored lesson based on what the user needs [6].

**Artifacts Produced:**
To manage this process, the agent continuously generates and updates several files on your local system:
*   **Mission:** A document defining the user's specific goals and motivations for learning [5].
*   **Resources:** A list of the web-searched materials the agent uses to build the lessons, which it continues to update as you go [5].
*   **Lessons:** A folder of individual HTML files containing the actual course material. Matt chose HTML because it is "so much richer than markdown it allows it to be so much more expressive so much more interactive" [5]. 
*   **Learning Record:** A file used to "keep track of how I'm doing and just like a real teacher then tailor the next lesson to what I need" [6, 7].
*   **Glossary:** A reference document storing "any weird jargon that we've learned" so that future lessons can be more concise [7, 8].
*   **Cheat Sheets:** Quick reference guides (like a "solve card") that provide "just a single place to look" for the complete steps [7].
*   **Notes (`notes.md`):** A document for the agent's "internal note-taking" to remember the user's preferences and potential watch-outs [7].

**How it Differs from Simply Asking Claude:**
Simply asking Claude to explain a topic is a **stateless** interaction, meaning the agent "doesn't retain any state from previous runs it doesn't have any memory of the things that you've done before" [1]. 

By contrast, `/teach` is specifically designed as a **stateful** skill. Matt emphasizes that effective teaching requires memory: "where I teach you i being the teacher I remember where you've got to i know what you've learned i know what you can go to next and I've got a bunch of great resources that I remember from previous times" [9]. By saving artifacts to the local file system, the `/teach` skill allows the agent to pick up exactly where you left off, creating a structured, evolving course rather than isolated explanations [1, 9].
